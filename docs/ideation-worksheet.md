# 1. 서비스 선정

## 1.1 어떤 서비스의 장애를 자동 복구할 것인가?

**서비스 이름:** Group Coffee Order Agent

**한 문장 설명:**

> 참여자가 채팅으로 커피 주문을 요청하면, 서비스는 모의 메뉴 데이터를 기준으로 메뉴·사이즈·옵션을 확정하고 누락과 오류를 검증하여 매장 제시용 최종 주문서를 반환한다.

**정상 실행 흐름:**

```text
참여자
  ↓
채팅 기반 주문 수집
  ↓
모의 메뉴 조회·정규화 → 모의 주문 저장 → 누락·중복·옵션 검증
  ↓
정상 결과: 참여자별 확정 내역과 메뉴별 합산 수량이 포함된 주문서
```

**핵심 의존 서비스:**

| 의존 대상 | 용도 | 실패 시 영향 | 모의 구현 여부 |
|---|---|---|---|
| 모의 메뉴 조회 서비스 | 메뉴명·사이즈·옵션 확인 및 정규화 | 주문을 확정할 수 없거나 처리가 지연됨 | 예 |
| 모의 주문 저장 서비스 | 참여자별 확정 주문 보관 | 주문이 누락되거나 저장에 실패함 | 예 |

## 1.2 서비스가 멈추면 어떤 영향이 발생하는가?

### 사용자 영향

- 주문 등록이 지연될 수 있다.
- 메뉴·사이즈·옵션이 확정되지 않거나 주문이 누락될 수 있다.

### 운영 영향

- 주문 총무가 로그와 주문 현황을 직접 확인해야 한다.
- 실패한 요청을 수동으로 재시도하고 최종 주문서를 다시 대조해야 한다.

### 데이터·비용·보안 영향

- 재처리 과정에서 주문이 중복 저장되거나 누락될 수 있다.
- 가상 이름과 모의 주문만 사용하며 실제 결제·개인정보·운영 데이터는 사용하지 않는다.

### 심각도

- [ ] 낮음 — 지연되지만 핵심 기능은 유지됨
- [x] 중간 — 일부 요청이 실패하고 운영자 대응이 필요함
- [ ] 높음 — 핵심 기능이 중단되거나 데이터·금전 피해 가능

**선택 근거:** 일부 주문이 실패하거나 잘못 집계될 수 있어 총무의 수동 확인이 필요하지만, 실제 주문·결제 및 개인정보 처리는 범위에서 제외한다.

# 2. 에이전트 설계

## 2.1 장애를 탐지하는 주체는 누구인가?

**에이전트 이름:** Monitor Agent

**관찰 데이터:**

- [x] 헬스체크 응답
- [x] 애플리케이션 로그
- [x] 오류율
- [x] 응답시간
- [x] 프로세스 상태
- [ ] 기타:

**장애 판정 조건:** HTTP 5xx, 3초를 초과한 메뉴 조회, 주문 저장소 연결 오류를 관찰하면 장애 사건을 생성한다.

**출력 메시지:** 사건 식별자, 탐지 시각, 대상 서비스, 관찰 신호, 장애 유형 후보가 포함된 장애 사건

---

## 2.2 원인을 진단하는 주체는 누구인가?

**에이전트 이름:** Diagnosis Agent

**입력:** Monitor Agent가 생성한 장애 사건과 관련 로그·응답 정보

**분류할 장애 유형:**

| 장애 코드 | 설명 | 판단 근거 | 신뢰도 또는 규칙 |
|---|---|---|---|
| MENU_HTTP_5XX | 모의 메뉴 조회 서비스가 5xx를 반환함 | HTTP 상태와 오류 로그 | 5xx 응답이 확인되면 분류 |
| MENU_TIMEOUT | 모의 메뉴 조회가 3초를 초과함 | 요청 시작·종료 시각 | 3초 초과 시 분류 |
| ORDER_STORE_CONNECTION | 모의 주문 저장 서비스에 연결할 수 없음 | 연결 오류와 저장 실패 로그 | 연결 오류가 확인되면 분류 |

**원인을 판단할 수 없을 때 행동:** 자동 변경을 수행하지 않고 증거와 함께 사람에게 에스컬레이션한다.

---

## 2.3 복구를 실행하는 주체는 누구인가?

**에이전트 이름:** Recovery Agent

**허용된 복구 행동:**

- 정책에 따라 실패한 조회 또는 저장 요청을 제한적으로 재시도한다.
- 허용목록에 등록된 모의 의존 서비스의 상태 회복 여부를 확인한다.
- 중복 저장을 방지하면서 실패한 저장 요청을 다시 처리한다.

**금지된 행동:**

- 임의로 생성한 쉘 명령을 실행하지 않는다.
- 실제 주문·결제·운영 데이터에 접근하거나 수정하지 않는다.
- 허용목록 밖의 서비스나 인프라를 재시작·변경하지 않는다.

**필요한 도구·API·명령:** 모의 메뉴 조회 및 주문 저장 인터페이스. 구체적인 도구와 명령은 상세 설계 단계에서 결정한다.

---

## 2.4 복구 성공을 독립적으로 검증하는 주체는 누구인가?

**에이전트 이름:** Verification Agent

**독립성이 필요한 이유:** Recovery Agent의 성공 보고만으로 사건을 종료하지 않고, 정상 요청과 주문 무결성을 별도로 확인하기 위해서다.

**검증 항목:**

- [x] 헬스체크 정상
- [x] 핵심 기능 테스트 통과
- [x] 오류율 정상 범위
- [x] 응답시간 정상 범위
- [x] 데이터 무결성 확인
- [ ] 회귀 테스트 통과

**복구 실패 판정 조건:** 독립 요청이 실패하거나, 응답시간·오류율 기준을 만족하지 못하거나, 주문 누락·중복·필수 옵션 오류가 남아 있는 경우. 구체적인 수치는 `[미결정]`이다.

## 2.5 오케스트레이터가 필요한가?

- [x] 필요함
- [ ] 필요하지 않음

**판단 근거:** 탐지·진단·복구·검증의 순서와 사건별 시도 제한, 회로 차단, 사람 에스컬레이션을 일관되게 관리해야 한다. 주문 처리 에이전트 4개는 유지하되, 장애 대응 역할은 구현 시 책임과 독립 검증 원칙을 훼손하지 않는 범위에서 통합할 수 있다.

### 오케스트레이터의 책임

- 장애 사건의 상태와 역할별 실행 순서를 관리한다.
- 재시도 상한, 전체 타임아웃, 회로 차단 정책을 적용한다.
- 복구 성공 또는 실패에 따라 종료하거나 사람에게 에스컬레이션한다.

### 오케스트레이터가 해서는 안 되는 일

- 승인된 정책과 권한 제한을 우회하지 않는다.
- 직접 복구 명령을 임의 생성하거나 주문 데이터를 수정하지 않는다.

## 2.6 에이전트 협업 구조

| 에이전트 | 입력 | 출력 | 호출 주체 | 허용 권한 | 타임아웃 |
|---|---|---|---|---|---:|
| Monitor | 상태·로그·응답 지표 | 장애 사건 | Orchestrator 또는 관찰 주기 | 조회, 사건 생성 | [미결정] |
| Diagnosis | 장애 사건과 증거 | 장애 분류와 복구 권고 | Orchestrator | 증거 조회, 분류 | [미결정] |
| Recovery | 승인된 복구전략 | 시도 결과와 증거 | Orchestrator | 제한된 재시도, 허용된 재처리 | [미결정] |
| Verification | 복구 결과와 정상 기준 | 정상화 또는 실패 판정 | Orchestrator | 독립 상태·기능 검증 | [미결정] |
| Notification | 사건 상태와 증거 | 승인 요청 또는 결과 보고 | Orchestrator | 사람에게 정보 전달 | [미결정] |

### 협업 흐름

```text
[장애 발생]
  ↓
[Monitor: 장애 사건 생성]
  ↓
[Diagnosis: 장애 유형 분류]
  ↓
[Recovery: 허용된 복구 실행]
  ↓
[Verification: 독립 검증]
  ├─ 성공 → [사건 종료 및 결과 보고]
  └─ 실패 → [정책 한도 확인 후 재시도 또는 사람 에스컬레이션]
```

## 5.2 장애 탐지부터 복구까지 걸린 시간을 어떻게 측정할 것인가?

```text
injected_at  = 장애가 모의 환경에 주입된 시각
detected_at  = Monitor Agent가 사건을 생성한 시각
recovery_started_at = Recovery Agent가 첫 복구를 시작한 시각
recovered_at = Verification Agent가 정상화를 확인한 시각
```

```text
MTTD = detected_at - injected_at
MTTR = recovered_at - injected_at
복구 실행시간 = recovered_at - recovery_started_at
```

**시간을 기록할 컴포넌트:** Orchestrator의 사건 이력

# 7. 최종 범위 선언

## 반드시 구현할 것

1. 구조화된 주문 수집부터 검증된 최종 주문서 생성까지의 최소 흐름
2. 지정된 세 가지 장애의 탐지·진단·제한된 복구·독립 검증
3. 사건 식별자와 탐지·복구·검증 이력을 포함한 추적 기록
4. 최대 20명의 주문을 총무가 수동으로 마감하는 기능
5. 화면용 Markdown 표와 시스템 처리를 위한 JSON 형식의 최종 주문서

## 구현하지 않을 것

1. 실제 스타벅스 시스템 연동과 실제 주문·결제·환불
2. 실제 개인정보·운영 데이터 사용과 운영 인프라 변경
3. 음성 주문, 범용 자유대화, 임의 명령 실행

## 성공 기준

1. 지정된 세 가지 장애 각각에 대해 탐지와 복구 성공 여부를 판정한다.
2. Recovery Agent와 독립된 Verification Agent가 정상화와 주문 무결성을 확인한다.
3. 각 사건의 MTTD, MTTR, 복구 시도, 최종 상태를 기록한다.

## 주요 위험과 대응

| 위험 | 가능성 | 영향 | 대응 |
|---|---|---|---|
| 주문 기능과 장애 대응 기능을 함께 구현해 범위가 커짐 | 높음 | 3일 내 완료 실패 | 구조화된 입력, 고정 메뉴, 모의 의존 서비스로 제한 |
| 재시도로 주문이 중복 저장됨 | 중간 | 주문서 오류 | 주문 식별자를 사용한 중복 방지와 독립 검증 요구 |
| 복구 정책 수치가 근거 없이 결정됨 | 중간 | 무한 반복 또는 조기 실패 | PRD 작성 전 시도 상한·시간 기준을 확정 |
