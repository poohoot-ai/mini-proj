# 1. 서비스 선정

## 1.1 어떤 서비스의 장애를 자동 복구할 것인가?

**서비스 이름:** 스타벅스 단체 주문 명세 자동화 시스템  

**한 문장 설명:**  

> 총무가 여러 사람의 주문을 자연어로 일괄 입력하면, 서비스는 모의 메뉴 데이터와 대조하여 메뉴·온도·사이즈·옵션을 정규화하고 동일 주문별 합산 명세서를 반환한다.

**정상 실행 흐름:**

```text
총무의 일괄 자연어 입력
  ↓
수집 → 메뉴 정규화 → 주문 검증 → 동일 주문 합산
  ↓
모의 메뉴 데이터와 주문 처리 상태 저장소
  ↓
정상 결과: 매장 직원에게 보여줄 수 있는 합산 주문 명세서
```

**핵심 의존 서비스:**

| 의존 대상 | 용도 | 실패 시 영향 | 모의 구현 여부 |
|---|---|---|---|
| 모의 스타벅스 메뉴 데이터 | 메뉴명·온도·사이즈·옵션 유효성 확인 | 메뉴 정규화와 옵션 검증 실패 | 예 |
| PostgreSQL | 메뉴 데이터와 주문 처리 상태 저장 | 메뉴 조회 및 상태 이어받기 실패 | 아니요(실제 개발 DB 사용 예정) |
| 에이전트 실행 환경 | 수집·정규화·검증·합산 처리 | 주문 처리 지연 또는 중단 | 일부 장애·폴백은 모의 검증 |
| 에이전트 간 상태 전달 | 원문·중간 결과·오류·재시도 상태 전달 | 주문자·옵션·수량 누락 또는 중복 가능 | 예 |

## 1.2 서비스가 멈추면 어떤 영향이 발생하는가?

### 사용자 영향

- 주문 명세서 생성이 지연되거나 중단된다.
- 주문자, 메뉴 또는 옵션이 누락되면 오주문과 재주문이 발생할 수 있다.

### 운영 영향

- 총무가 원문을 다시 확인하고 주문서를 수작업으로 작성해야 한다.
- 장애가 반복되면 어느 처리 단계에서 실패했는지 사람이 추적해야 한다.

### 데이터·비용·보안 영향

- 실제 결제와 실명·연락처 등 개인정보는 처리하지 않는다.
- 잘못된 주문으로 현장 비용과 재주문이 발생할 수 있다.
- 시크릿은 코드·이미지·일반 로그에 포함하지 않아야 한다.

### 심각도

- [ ] 낮음 — 지연되지만 핵심 기능은 유지됨
- [x] 중간 — 일부 요청이 실패하고 운영자 대응이 필요함
- [ ] 높음 — 핵심 기능이 중단되거나 데이터·금전 피해 가능

**선택 근거:** 핵심 주문 처리가 실패하면 총무의 수작업이 필요하고 오주문 가능성이 있지만, 실제 결제·운영 개인정보·매장 주문 API는 범위에서 제외한다.

### 포함 범위

- 총무가 여러 사람의 주문을 자연어로 한 번에 입력한다.

# 2. 에이전트 설계

## 2.1 주문 업무 에이전트

| 에이전트 | 책임 | 주요 입력 | 주요 출력 | 금지 행동 |
|---|---|---|---|---|
| 수집 에이전트 | 일괄 자연어 입력을 주문자별 주문으로 분리 | 총무의 원문 | 주문자별 원문 목록 | 원문에 없는 주문자·메뉴 생성 |
| 메뉴 정규화 에이전트 | 메뉴·온도·사이즈·옵션을 모의 메뉴와 매칭 | 주문자별 원문, 메뉴 데이터 | 정규화 주문 또는 재질문 필요 상태 | 불명확한 주문 임의 확정 |
| 주문 검증 에이전트 | 누락·중복·모순 및 주문자 집합 일치 확인 | 원문, 정규화 결과 | 검증 결과와 재질문 항목 | 검증되지 않은 주문을 정상 선언 |
| 정산 에이전트 | 동일 주문을 합산하여 최종 명세서 생성 | 검증된 주문 목록 | 합산 주문 명세서 | 가격·결제·실제 매장 주문 수행 |

> 주문 검증 에이전트는 주문 내용의 정확성을 검사한다. 장애 복구 완료를 판정하는 독립 검증 역할과는 구분한다.

## 2.2 장애를 탐지하는 주체는 누구인가?

**제어 컴포넌트:** Orchestrator와 Docker `HEALTHCHECK`. `HEALTHCHECK`는 컨테이너의 `healthy`·`unhealthy` 상태를 판정하고, Orchestrator는 에이전트 타임아웃·DB·LLM·Handoff 오류를 판정한다. 별도의 LLM Monitor 에이전트는 두지 않는다.  

**관찰 데이터:**

- [x] 헬스체크 응답
- [x] 애플리케이션 로그
- [x] 오류율
- [x] 응답시간
- [x] 에이전트 실행 상태
- [x] 기타: DB 연결 상태, LLM·프롬프트 처리 상태, Handoff 필수 필드

**장애 판정 조건:** 에이전트별 10초 제한시간 초과, 명시적 실패 상태, PostgreSQL·메뉴 조회 실패, Handoff 필수 필드 누락, 동일 장애의 3회 연속 발생.  

**출력 메시지:** incident_id, trace_id, 장애 유형, 발생 단계, 탐지 근거, 현재 시도 횟수, 영향받은 주문 처리 상태

---

## 2.3 원인을 진단하는 주체는 누구인가?

**제어 컴포넌트:** Orchestrator의 규칙 기반 장애 분류. 별도의 LLM Diagnosis 에이전트는 두지 않는다.  

**입력:** 장애 사건, 에이전트 상태, 애플리케이션 로그, DB 연결 상태, Handoff 상태, 재시도 이력

**분류할 장애 유형:**

| 장애 코드 | 설명 | 판단 근거 | 신뢰도 또는 규칙 |
|---|---|---|---|
| AGENT_TIMEOUT | 에이전트 응답 지연 | 제한시간 내 응답 없음 | 10초 초과 |
| AGENT_FAILURE | 에이전트 처리 실패 | 실패 상태 또는 유효하지 않은 결과 | 명시적 오류 또는 결과 검증 실패 |
| MENU_DB_FAILURE | PostgreSQL·메뉴 데이터 조회 실패 | 연결·조회 오류 | DB·조회 오류 신호 |
| REPEATED_FAILURE | 동일 장애 반복 | 동일 trace 또는 사건의 연속 실패 | 3회 연속 실패 |

**원인을 판단할 수 없을 때 행동:** 자동 변경 없이 안전 중단하고, 증거와 주문 처리 상태를 사람에게 전달한다.

---

## 2.4 복구를 실행하는 주체는 누구인가?

**제어 컴포넌트:** Orchestrator의 허용목록 기반 복구정책과 컨테이너 재시작 정책. Docker `HEALTHCHECK`는 상태를 감지하지만 그 자체로 컨테이너를 재시작하지 않는다. 종료된 컨테이너는 재시작 정책이 처리하고, 실행 중인 `unhealthy` 컨테이너의 교체 방식은 최종 AWS 배포 환경에서 결정한다. 에이전트 타임아웃·DB·LLM 오류는 Orchestrator가 처리한다. 별도의 LLM Recovery 에이전트는 두지 않는다.  

**허용된 복구 행동:**

- 정해진 상한 내에서 같은 입력을 재시도
- PostgreSQL·메뉴 데이터 연결 재시도
- 모의 대체 모델로 전환
- 회로 차단 후 자동 실행 중지

**금지된 행동:**

- 임의 쉘 명령 생성·실행
- 운영 데이터 임의 수정·삭제
- 실제 결제나 매장 주문 수행
- 인증정보 변경
- 비용 제한 없는 AWS 리소스 생성
- 허용목록 밖 서비스 재시작

**필요한 도구·API·명령:** 허용된 재시도·재연결·모의 대체 모델 인터페이스. 구체 도구와 명령은 후속 설계 단계에서 결정한다.

---

## 2.5 복구 성공을 독립적으로 검증하는 주체는 누구인가?

**제어 컴포넌트:** Orchestrator가 호출하는 결정적 Recovery Verification Gate. 별도의 LLM 에이전트는 두지 않되 복구 실행 로직과 분리한다.  

**독립성이 필요한 이유:** 복구 실행 역할의 자기보고만으로 장애를 종료하면 부분 복구, 중복 집계 또는 주문 상태 손상을 놓칠 수 있다.  

**검증 항목:**

- [x] 헬스체크 정상
- [x] 핵심 주문 흐름 정상
- [x] 오류율 정상 범위
- [x] 응답시간 정상 범위
- [x] 주문자 집합과 주문 상태 무결성 확인
- [x] 필수 검증 통과

**복구 실패 판정 조건:** 헬스체크 또는 주문 흐름 실패, 주문자 누락·중복, 원문과 결과의 주문자 집합 불일치, 응답시간·오류율 기준 미충족. 구체 임계치는 [미결정].

## 2.6 오케스트레이터가 필요한가?

- [x] 필요함
- [ ] 필요하지 않음

**판단 근거:** 주문 업무 에이전트의 순서와 Handoff를 관리하고, 장애 발생 시 시도 횟수·폴백·회로 차단·에스컬레이션을 일관되게 통제해야 한다.

### 오케스트레이터의 책임

- 주문 처리와 복구 흐름의 순서·상태·제한시간 관리
- trace_id 기반 Handoff와 중간 결과 보존 확인
- 재시도 상한, 회로 차단, 사람 에스컬레이션 집행

### 오케스트레이터가 해서는 안 되는 일

- 정책을 우회하여 무제한 재시도하거나 임의 복구 실행
- 주문 검증 또는 복구 검증을 생략하고 완료 선언
- 주문 원문이나 검증 결과를 임의 변경

|---|---|---|---|---|---:|

| 메뉴 정규화 에이전트 | 주문자별 원문, 메뉴 데이터 | 정규화 주문·재질문 | Orchestrator | 메뉴 조회, 정규화 | 10초 |
| 주문 검증 에이전트 | 원문, 정규화 결과 | 검증 결과 | Orchestrator | 읽기·대조 | 10초 |
| 정산 에이전트 | 검증된 주문 | 합산 명세서 | Orchestrator | 합산·출력 | 10초 |
| Docker HEALTHCHECK·컨테이너 재시작 제어 | 상태·헬스체크·지표 | 건강 상태·재시작 결과 | Docker·최종 배포 런타임 | 상태 판정, 정책에 따른 재시작 | 10초 감지 기준 |
| Recovery Verification Gate | 복구 결과·원본 상태 | 독립 검증 결과 | Orchestrator | 읽기·결정적 검증 | 10초 |
| Notification control | 사건·결과·증거 | 사람 알림 | Orchestrator | 지정 채널 알림 | [미결정] |

> 멀티 에이전트의 핵심 역할은 수집·메뉴 정규화·주문 검증·정산의 네 개다. Orchestrator, Docker `HEALTHCHECK`, 장애 분류, 복구 실행, 복구 검증, 알림은 결정적 제어 컴포넌트이며 별도의 LLM 에이전트로 계산하지 않는다.

### Handoff 필수 컨텍스트

- trace_id와 incident_id(장애 발생 시)
- 주문 원문과 주문자 식별자
- 정규화된 메뉴·온도·사이즈·옵션
- 현재 단계와 처리 상태
- 중간 결과와 결과 버전
- 오류 유형과 근거
- 재시도 횟수와 사용한 폴백

### 협업 흐름

```text
총무 입력
  ↓
수집 → 메뉴 정규화 → 주문 검증 → 정산
  ↓ 장애 감지
Docker HEALTHCHECK 또는 Orchestrator 감지 → 규칙 기반 복구 → Recovery Verification Gate
  ├─ 성공 → 중단 지점부터 안전하게 재개
  └─ 실패/상한 도달 → 회로 차단 → 사람 에스컬레이션
```

## 5.2 장애 탐지부터 복구까지 걸린 시간을 어떻게 측정할 것인가?

```text
injected_at = 장애가 모의 주입된 시각
detected_at = Monitor가 사건을 생성한 시각
recovery_started_at = 첫 복구 행동을 시작한 시각
recovered_at = 독립 검증이 정상화를 확인한 시각
```

```text
MTTD = detected_at - injected_at
MTTR = recovered_at - injected_at
복구 실행시간 = recovered_at - recovery_started_at
```

**시간을 기록할 컴포넌트:** 오케스트레이터와 사건·추적 저장소

# 7. 최종 범위 선언

## 반드시 구현할 것

1. 총무의 일괄 자연어 주문을 정규화하고 동일 주문별로 합산하는 멀티 에이전트 흐름
2. 메뉴·옵션 검증, 기본 톨 적용, 모호한 주문 재질문, 주문자 누락·중복 방지
3. 네 가지 장애의 탐지·제한적 복구·회로 차단·독립 검증·에스컬레이션
4. Handoff 컨텍스트와 주문 처리 상태의 추적 가능성
5. 자동 복구율 및 품질 기준을 증명할 수 있는 결과 기록

## 구현하지 않을 것

1. 개인별 채팅 주문 수집과 확정된 프론트엔드
2. 실제 스타벅스 API·매장 주문·가격 계산·결제
3. 임의 명령 기반 완전 자율 복구

## 성공 기준

1. 입력 주문자의 집합과 최종 명세서의 주문자 집합이 일치하고 중복이 없다.
2. 사이즈 미입력 시 톨이 적용되고, 그 외 모호한 정보는 임의 확정하지 않고 재질문한다.
3. 네 가지 장애 시나리오에서 탐지·복구 또는 안전 중단 결과와 MTTD·MTTR을 기록한다.
4. 자동 복구 성공률 85% 이상을 목표로 한다.
5. 파이프라인의 테스트 커버리지 85% 이상을 목표로 한다.

| 배포 및 장애 복구 보고서 | 멀티 컨테이너, 서비스 연결, 시크릿, 감지 지표, 복구정책, 복구 KPI | 실제 배포 구성과 장애별 복구 결과 |
| 파이프라인 구현 결과 보고서 | 단계별 입출력·실패 처리, 품질 게이트, 알림·담당자·에스컬레이션 | 파이프라인 다이어그램과 실행 결과 |

> 별도의 `장애 복구 보고서`는 만들지 않는다. 관련 설계·실험·결과는 `배포 및 장애 복구 보고서`에 포함한다.
