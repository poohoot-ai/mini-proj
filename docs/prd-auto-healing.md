## 2. 프로젝트 개요

총무가 10명 이상의 단체 주문을 취합할 때 여러 사람이 구글 스프레드시트에 이름과 메뉴를 입력하고, 총무가 그 내용을 직접 확인해 매장에서 주문하는 과정에는 누락·중복·오주문 위험이 있다.

본 프로젝트는 총무가 여러 사람의 주문을 자연어로 한 번에 입력하면 네 개의 핵심 에이전트가 주문을 분리·정규화·검증·합산하여 매장 직원에게 보여줄 수 있는 주문 명세서를 만드는 시스템을 정의한다. 에이전트 또는 의존 서비스가 지연되거나 실패하더라도 Orchestrator와 결정적 제어 컴포넌트가 제한된 복구정책을 적용하고, 복구 결과를 독립 검증한 뒤에만 처리를 재개한다.

**한 문장 정의:**

> 총무가 여러 사람의 주문을 자연어로 일괄 입력하면, 시스템은 모의 메뉴 데이터와 대조하여 메뉴·온도·사이즈·옵션을 정규화하고 동일 주문별 합산 명세서를 반환한다.

**기술 제약조건:**

- 백엔드: Python, FastAPI
- 프론트엔드: Streamlit
- 데이터베이스: PostgreSQL
- 배포 환경: AWS EC2 단일 인스턴스와 Docker Compose
- 주 LLM: OpenAI API `gpt-4o-mini`(구현 전 계정 가용성 확인 필요)
- 컨테이너 상태 감지: Docker `HEALTHCHECK`
- 실제 스타벅스 API 대신 모의 메뉴 데이터 사용

## 3. 문제 정의

### 3.1 사용자 문제

- 여러 주문자가 동시에 스프레드시트를 수정하므로 입력 형식이 일관되지 않다.
- `아아`, `뜨아`와 같은 약칭과 자연어 옵션을 총무가 수동으로 해석해야 한다.
- 주문자 누락, 옵션 누락, 잘못된 합산을 매장 주문 전까지 발견하지 못할 수 있다.
- 총무가 스프레드시트를 직접 확인하며 주문하기 때문에 현장 주문 시간이 길어진다.

### 3.2 운영 문제

- 주문 처리 에이전트가 지연되거나 실패하면 실패 위치와 영향을 받은 주문을 사람이 찾기 어렵다.
- 무제한 재시도는 중복 집계와 장애 확산을 일으킬 수 있다.
- 복구 실행 주체의 성공 보고만으로는 주문 상태가 실제로 정상인지 보장할 수 없다.
- 네트워크·DB·API·LLM·프롬프트 유형별 장애 근거가 보존되지 않으면 재발 분석이 어렵다.

### 3.3 서비스 경계

서비스는 총무의 일괄 자연어 입력을 받아 합산 주문 명세서를 반환하는 데서 끝난다. 실제 가격 계산, 결제, 스타벅스 시스템 연결, 매장 주문 전송은 수행하지 않는다.

## 5. 목표와 성공 기준

### 5.1 목표

1. 총무의 자연어 일괄 입력을 주문자별로 분리하고 정식 메뉴 정보로 정규화한다.
2. 주문자 누락·중복과 메뉴·옵션 불일치를 최종 합산 전에 발견한다.
3. 동일한 메뉴·온도·사이즈·옵션을 하나의 행으로 합산한다.
4. 지정된 네 가지 장애 시나리오에서 탐지·제한적 복구·안전 중단 여부를 판정한다.
5. 장애의 탐지 시점, 복구 시도, 정상화 시점, 독립 검증 결과를 보존한다.
6. 최종 산출물이 PRD 요구사항을 어떻게 증명하는지 추적할 수 있게 한다.

### 5.2 측정 가능한 성공 기준

| ID | 기준 | 목표 |
|---|---|---|
| SC-001 | 주문자 무결성 | 입력 주문자 집합과 최종 결과 주문자 집합 100% 일치, 중복 0건 |
| SC-002 | 기본 사이즈 | 사이즈 미입력 주문에 톨 적용률 100% |
| SC-003 | 모호성 처리 | 확정할 수 없는 메뉴·옵션을 임의 확정하지 않고 재질문 상태로 전환 |
| SC-004 | 성능 | 최대 30명 입력에서 전체 명세서 생성 p95 20초 이내 |
| SC-005 | 정상 오류율 | 1% 미만 |
| SC-006 | 자동 복구 성공률 | 자동 복구 대상 3종을 각 10회씩 총 30회 실행하여 85% 이상 |
| SC-006A | 반복 장애 안전 통제 | 반복 장애 실험에서 회로 차단 성공률 100% |
| SC-007 | 품질 기준 | 파이프라인에서 측정하는 테스트 커버리지 85% 이상 |
| SC-008 | 추적성 | 모든 장애에 incident_id·trace_id·탐지·복구·검증 결과 존재 |
| SC-009 | 안전성 | 최대 시도 초과 시 추가 자동 실행 없이 회로 차단 및 사람에게 수동 확인 요청 |

## 7. 정상 서비스 시나리오

### 7.1 입력 예시

```text
민수는 아아, 서연은 뜨아, 지훈은 따뜻한 카페모카 휘핑 빼고,
수빈은 콜드브루, 현우는 아아에 샷추가, 지민은 뜨아
```

### 7.2 정상 처리 흐름

```text
총무의 Streamlit 일괄 입력
→ Orchestrator가 trace_id 생성
→ 수집 에이전트가 주문자별 원문 분리
→ 메뉴 정규화 에이전트가 모의 메뉴 데이터와 대조
→ 주문 검증 에이전트가 누락·중복·모순 확인
→ 정산 에이전트가 동일 주문별 합산
→ Recovery Verification Gate가 처리 상태와 주문자 무결성 확인
→ 최종 주문 명세서 반환
```

### 7.3 정상 결과 예시

```text
총 인원 수: 6명

아이스 | 톨 | 아메리카노 | 1잔 | 민수
따뜻한 | 톨 | 아메리카노 | 2잔 | 서연, 지민
따뜻한 | 톨 | 카페모카 | 휘핑 제외 | 1잔 | 지훈
아이스 | 톨 | 콜드브루 | 1잔 | 수빈
아이스 | 톨 | 아메리카노 | 샷 추가 | 1잔 | 현우
```

사이즈가 없으면 톨을 적용한다. 그 밖의 메뉴·온도·옵션이 확정되지 않으면 결과를 임의 생성하지 않고 총무에게 재질문한다.

## 8. 장애 시나리오

| ID | 장애 | 발생 위치 | 탐지 신호 | 사용자·운영 영향 | 안전한 재현 방향 |
|---|---|---|---|---|---|
| FS-001 | 에이전트 응답 지연·타임아웃 | 수집·정규화·검증·정산 | 10초 내 응답 없음 | 명세서 생성 지연 | 모의 응답 지연 |
| FS-002 | 에이전트 처리 실패 | 주문 처리 단계 | 명시적 실패 상태 또는 유효하지 않은 결과 | 일부 주문 처리 중단 | 모의 실패 응답 |
| FS-003 | PostgreSQL·메뉴 조회 실패 | 메뉴 정규화·상태 저장 | 연결·조회 오류 | 메뉴 검증 및 처리 상태 기록 중단 | 모의 연결·조회 실패 |
| FS-004 | 동일 장애 반복 | 전체 흐름 | 같은 사건에서 3회 연속 실패 | 무한 복구 루프 위험 | 같은 실패의 연속 발생 |

장애 재현은 모의 환경과 가명 주문 데이터만 사용하며 실제 결제·운영 데이터에 영향을 주지 않아야 한다.

## 9. 멀티 에이전트 구성

### 9.1 Orchestrator

- 책임: 실행 순서, trace_id, 상태, 제한시간, 재시도, 회로 차단, Handoff 관리
- 입력: 총무 원문, 각 단계 결과, 장애 신호
- 출력: 다음 역할 호출, 복구 결정, 최종 처리 상태
- 사용할 수 있는 정보: 주문 원문, 중간 결과, 재시도 이력, 헬스·오류 신호
- 허용 행동: 핵심 에이전트 호출, 제한된 재시도, 모의 대체 모델 전환, 회로 차단, 검증 게이트 호출
- 금지 행동: 주문 내용 임의 수정, 무제한 재시도, 검증 생략, 임의 인프라 변경
- 실패 시 행동: 처리 상태를 보존하고 사람에게 수동 확인 요청

> Orchestrator는 실행 제어 컴포넌트이며 핵심 업무 에이전트 수에 포함하지 않는다.

### 9.2 수집 에이전트

- 책임: 총무의 일괄 자연어 입력을 주문자별 원문으로 분리
- 입력: 총무 원문, trace_id
- 출력: 주문자별 원문 목록
- 사용할 수 있는 정보: 입력 원문과 Handoff 메타데이터
- 허용 행동: 텍스트 분리, 주문자 표기 추출
- 금지 행동: 원문에 없는 주문자·메뉴·옵션 생성
- 실패 시 행동: 명시적 실패 상태와 근거 반환

### 9.3 메뉴 정규화 에이전트

- 책임: 약칭을 메뉴명으로 변환하고 온도·사이즈·옵션 확정
- 입력: 주문자별 원문, 모의 메뉴 데이터
- 출력: 정규화 주문 또는 재질문 필요 상태
- 사용할 수 있는 정보: 메뉴·옵션 데이터, 기본 톨 정책
- 허용 행동: 메뉴 조회, 정규화, 허용된 기본값 적용
- 금지 행동: 불명확한 메뉴·옵션 임의 확정
- 실패 시 행동: 확정되지 않은 필드와 재질문 내용을 반환

### 9.4 주문 검증 에이전트

- 책임: 주문자 누락·중복·모순 및 입력·결과 주문자 집합 일치 검사
- 입력: 원문, 주문자별 원문, 정규화 결과
- 출력: 검증 통과 또는 오류·재질문 목록
- 사용할 수 있는 정보: 이전 단계 결과와 메뉴 유효성 정보
- 허용 행동: 읽기·대조·검증
- 금지 행동: 검증 실패 결과를 정상으로 변경
- 실패 시 행동: 최종 합산 중단과 검증 근거 반환

### 9.5 정산 에이전트

- 책임: 동일 메뉴·온도·사이즈·옵션별 주문을 합산해 명세서 생성
- 입력: 검증된 주문 목록
- 출력: 합산 주문 명세서
- 사용할 수 있는 정보: 검증 완료 주문만 사용
- 허용 행동: 그룹화·수량 합산·출력 정렬
- 금지 행동: 가격 계산, 결제, 실제 매장 주문
- 실패 시 행동: 부분 결과를 최종 결과로 반환하지 않고 실패 상태 반환

### 9.6 결정적 제어 컴포넌트

| 컴포넌트 | 책임 | 비고 |
|---|---|---|
| Docker `HEALTHCHECK` | 컨테이너 건강 상태 판정 | 상태 감지이며 그 자체가 재시작을 수행하지 않음 |
| 컨테이너 재시작 정책 | 종료된 컨테이너 재시작 | 실행 중인 unhealthy 컨테이너는 회로 차단 후 운영 담당자가 수동 확인 |
| 규칙 기반 장애 분류 | 타임아웃·처리 실패·DB 실패·반복 실패 분류 | 별도 LLM Diagnosis 에이전트를 두지 않음 |
| Recovery Verification Gate | 복구 후 헬스·핵심 흐름·주문 무결성 독립 검증 | 복구 실행 로직과 분리 |
| 수동 확인 상태 저장 | 장애·복구·수동 확인 필요 상태 기록 | API 상태와 구조화 로그로 조회하며 외부 자동 알림은 제외 |

## 10. 에이전트 협업 흐름

### 10.1 Handoff 필수 컨텍스트

모든 Handoff에는 다음 정보가 누락 없이 전달되어야 한다.

- trace_id
- incident_id(장애 발생 시)
- 주문 원문과 주문자 식별자
- 정규화된 메뉴·온도·사이즈·옵션
- 현재 단계와 처리 상태
- 중간 결과와 결과 버전
- 오류 유형과 판단 근거
- 현재 시도 횟수와 사용한 복구전략

### 10.2 협업 원칙

1. 이전 단계의 필수 컨텍스트가 누락되면 다음 단계로 진행하지 않는다.
2. 정산 에이전트는 주문 검증을 통과한 결과만 사용한다.
3. 같은 trace_id의 같은 단계가 재시도되더라도 결과가 중복 집계되지 않아야 한다.
4. 복구 실행 결과는 Recovery Verification Gate를 통과하기 전까지 정상으로 확정하지 않는다.
5. 복구 검증 실패 또는 시도 상한 도달 시 자동 처리를 중단한다.

### 10.3 장애 포함 흐름

```text
핵심 에이전트 실행
  ↓
Docker HEALTHCHECK 또는 Orchestrator의 장애 감지
  ↓
규칙 기반 장애 분류
  ↓
허용된 재시도·재연결·모의 대체 모델
  ↓
Recovery Verification Gate
  ├─ 성공 → 중단 지점부터 안전하게 재개
  └─ 실패/상한 도달 → 회로 차단 → 사람에게 수동 확인 요청
```

## 13. 기능 요구사항

### FR-001 일괄 주문 입력

- 설명: 총무가 여러 사람의 주문을 자연어로 한 번에 제출한다.
- 입력: 주문자 표기와 주문 내용이 포함된 자연어
- 기대 동작: 하나의 trace_id로 처리 시작
- 예외 상황: 빈 입력 또는 주문자 식별 불가
- 인수조건: 유효 입력이 수집 에이전트로 한 번만 전달되고 원문이 보존된다.

### FR-002 주문자별 분리

- 설명: 일괄 입력을 주문자별 원문으로 분리한다.
- 입력: 총무의 원문
- 기대 동작: 각 주문자가 하나의 주문 원문과 연결된다.
- 예외 상황: 주문자 또는 주문 내용 누락
- 인수조건: 추출된 주문자 집합을 원문과 대조할 수 있고 누락 의심 항목을 표시한다.

### FR-003 메뉴 정규화

- 설명: 메뉴 약칭과 자연어 옵션을 모의 메뉴 데이터의 정식 표현으로 변환한다.
- 입력: 주문자별 원문, 메뉴 데이터
- 기대 동작: 메뉴·온도·사이즈·옵션을 구조화한다.
- 예외 상황: 존재하지 않거나 복수 의미인 메뉴·옵션
- 인수조건: 확정 가능한 항목만 정규화하고 불명확한 항목은 재질문 상태로 반환한다.

### FR-004 기본 사이즈 적용

- 설명: 주문에 사이즈가 없으면 톨을 적용한다.
- 입력: 사이즈가 없는 정규화 대상 주문
- 기대 동작: 사이즈를 톨로 기록한다.
- 예외 상황: 사용자가 다른 사이즈를 명시함
- 인수조건: 명시된 사이즈를 덮어쓰지 않고 미입력 주문에만 톨을 적용한다.

### FR-005 모호한 주문 재질문

- 설명: 임의 확정이 위험한 주문을 총무에게 되묻는다.
- 입력: 불명확 필드와 근거
- 기대 동작: 주문자와 확인할 항목이 포함된 질문을 생성한다.
- 예외 상황: 응답 없음
- 인수조건: 답변 전까지 해당 주문을 최종 합산하지 않는다.

### FR-006 주문 무결성 검증

- 설명: 누락·중복·모순 및 주문자 집합 일치를 검사한다.
- 입력: 원문, 분리 결과, 정규화 결과
- 기대 동작: 통과 또는 오류 목록 반환
- 예외 상황: 필수 Handoff 컨텍스트 누락
- 인수조건: 입력과 결과의 주문자 집합이 다르면 정산 단계가 시작되지 않는다.

### FR-007 동일 주문 합산

- 설명: 메뉴·온도·사이즈·옵션이 모두 같은 주문을 합산한다.
- 입력: 검증 완료 주문
- 기대 동작: 총 인원 수와 수량·주문자 목록이 포함된 합산 명세서 생성
- 예외 상황: 옵션이 다른 주문
- 인수조건: 옵션이 다르면 별도 행으로 유지하고, 표시된 총 인원 수와 주문자 수 합계가 입력 주문자 수와 일치한다.

### FR-008 Handoff 컨텍스트 보존

- 설명: 에이전트 간 상태·중간 결과·오류 정보를 전달한다.
- 입력: 현재 단계 결과와 메타데이터
- 기대 동작: 필수 컨텍스트를 다음 단계에 전달하고 상태 버전을 기록한다.
- 예외 상황: 필수 필드 누락
- 인수조건: 필수 필드 누락 시 다음 단계 호출이 차단되고 장애 사건이 생성된다.

### FR-009 장애 감지와 분류

- 설명: 컨테이너·에이전트·DB·LLM·Handoff 장애를 구분한다.
- 입력: `HEALTHCHECK`, 응답시간, 오류·로그·상태
- 기대 동작: incident_id와 분류·근거 생성
- 예외 상황: 원인 불명
- 인수조건: 원인 불명 사건은 자동 변경 없이 수동 확인 상태로 전환한다.

### FR-010 제한적 복구

- 설명: 허용목록에 있는 재시도·재연결만 수행한다.
- 입력: 분류된 장애, 현재 시도 횟수
- 기대 동작: 정해진 상한과 대기정책 적용
- 예외 상황: 시도 상한 도달
- 인수조건: 최초 포함 3회를 초과하지 않고 모든 시도와 결과가 기록된다.

### FR-011 모의 대체 모델 폴백

- 설명: LLM·에이전트 실패 시 모의 대체 모델 경로를 검증한다.
- 입력: 실패한 요청과 마지막 확정 상태
- 기대 동작: 같은 입력을 모의 대체 모델로 처리
- 예외 상황: 대체 모델도 실패
- 인수조건: 대체 결과가 주문 검증과 Recovery Verification Gate를 모두 통과해야 한다.

### FR-012 회로 차단

- 설명: 반복 실패 시 자동 실행을 중단한다.
- 입력: incident별 실패·시도 이력
- 기대 동작: 3회 연속 실패 시 회로 열림 상태 전환
- 예외 상황: 냉각시간 중 새 요청
- 인수조건: 냉각시간 60초 동안 같은 자동 복구가 추가 실행되지 않는다.

### FR-013 독립 복구 검증

- 설명: 복구 실행 로직과 분리된 게이트가 정상화를 확인한다.
- 입력: 복구 결과, 헬스 상태, 원문과 주문 상태
- 기대 동작: 정상 또는 복구 실패 판정
- 예외 상황: 주문자 누락·중복 또는 기능 실패
- 인수조건: 검증 통과 전에는 사건을 종료하거나 최종 명세서를 반환하지 않는다.

### FR-014 수동 확인 상태 기록

- 설명: 자동 복구 실패와 모호한 주문을 사람이 조회할 수 있는 상태로 기록한다.
- 입력: 사건·주문·복구 이력·추천 행동
- 기대 동작: API 상태와 구조화 로그에 수동 확인 필요 여부와 근거 저장
- 예외 상황: 상태 또는 로그 저장 실패
- 인수조건: 외부 자동 알림 없이도 수동 확인 대상·원인·복구 이력·추천 행동을 조회할 수 있다.

### FR-015 컨테이너 건강 상태 제공

- 설명: 컨테이너가 `HEALTHCHECK`로 건강 상태를 제공한다.
- 입력: 서비스 및 핵심 의존성 상태
- 기대 동작: 정상·비정상 상태 판정 근거 제공
- 예외 상황: 확인 자체가 제한시간 초과
- 인수조건: 비정상 상태가 장애 사건의 증거로 연결되고, 재시작 여부는 배포 런타임 정책과 구분된다.

### FR-016 Streamlit 사용자 화면

- 설명: 총무가 자연어 주문을 입력하고 처리 결과와 수동 확인 필요 상태를 확인하는 화면을 제공한다.
- 입력: 일괄 자연어 주문, 모호한 주문에 대한 추가 답변
- 기대 동작: 주문 입력·제출, 처리 상태, 재질문, 총 인원 수와 합산 주문 명세서를 한 화면 흐름에서 제공한다.
- 예외 상황: API 응답 지연·실패 또는 회로 차단 상태
- 인수조건: 오류를 정상 결과처럼 표시하지 않고 trace_id와 사용자 행동 지침을 보여주며, 검증된 결과만 최종 명세서로 표시한다.

## 14. 비기능 요구사항

### NFR-001 성능

- 최대 30명 주문 입력에서 정상 상태의 전체 명세서 생성시간은 p95 20초 이내여야 한다.
- 개별 에이전트 호출의 제한시간은 10초여야 한다.

### NFR-002 신뢰성

- 타임아웃·에이전트 실패·DB 일시 장애를 각각 10회씩 총 30회 실험하고 자동 복구 성공률 85% 이상을 목표로 한다.
- 반복 장애는 자동 복구율 분모에서 제외하고 회로 차단 성공률 100%로 별도 측정한다.
- 같은 요청의 재시도가 중복 주문을 만들지 않아야 한다.
- 장애가 한 에이전트에서 발생해도 마지막 확정 주문 상태를 훼손하지 않아야 한다.

### NFR-003 안전성

- 재시도 상한, 회로 차단, 냉각시간을 우회할 수 없어야 한다.
- 허용목록 밖 복구와 임의 명령 실행을 금지해야 한다.
- 복구 검증 없이 정상화를 선언할 수 없어야 한다.

### NFR-004 관측 가능성

- 네트워크·DB·API·LLM·프롬프트·Handoff 오류를 분류 가능한 신호로 남겨야 한다.
- MTTD와 MTTR 계산에 필요한 네 개 시각을 기록해야 한다.
- 각 단계의 입력 참조, 출력 상태, 오류 근거, 소요시간을 trace_id로 연결해야 한다.
- 주문·사건·복구 이력은 PostgreSQL에 구조화해 저장하고, 애플리케이션·컨테이너 원본 로그는 Docker `local` 로깅 드라이버에 분리해야 한다.
- PostgreSQL 데이터는 Docker named volume으로 영속화해야 한다.

### NFR-005 보안

- 시크릿을 코드·이미지·일반 로그에 포함하지 않아야 한다.
- 실제 개인정보 대신 가명 주문자를 사용해야 한다.
- 실제 결제정보와 스타벅스 인증정보를 수집하지 않아야 한다.

### NFR-006 재현성

- 네 가지 장애 시나리오를 데이터 손상 없이 반복 재현할 수 있어야 한다.
- 같은 기준 입력과 장애 조건에서 성공·실패 판정 기준이 일관되어야 한다.

### NFR-007 설명 가능성

- 메뉴 정규화, 재질문, 장애 분류, 복구전략 선택의 근거를 사람이 확인할 수 있어야 한다.

### NFR-008 파이프라인 품질

- 테스트 커버리지 85% 미만 또는 필수 검증 실패 시 배포 단계로 진행하지 않아야 한다.
- 커밋→빌드→검증→배포 단계별 입력·출력·실패 상태를 기록할 수 있어야 한다.

## 15. 데이터와 로그 요구사항

### 15.1 주문 데이터

- 주문자 가명 식별자
- 원문 주문
- 정규화된 메뉴·온도·사이즈·옵션
- 검증 상태와 재질문 항목
- 합산 그룹과 주문자 목록
- 상태 버전과 마지막 확정 단계

### 15.2 사건·추적 데이터

- incident_id, trace_id
- injected_at, detected_at, recovery_started_at, recovered_at
- 장애 유형, 발생 단계, 탐지·진단 근거
- 선택한 복구전략, 시도 횟수, 대기시간
- 모의 대체 모델 사용 여부
- 사람 승인·수동 확인 요청 상태
- Recovery Verification Gate 결과
- 최종 상태와 소요시간

### 15.3 시간 지표

```text
MTTD = detected_at - injected_at
MTTR = recovered_at - injected_at
복구 실행시간 = recovered_at - recovery_started_at
```

### 15.4 로그 정책

- 구조화 기록 저장: Docker 내부 PostgreSQL의 주문·사건·복구 이력 테이블
- 원본 로그 저장: Docker `local` 로깅 드라이버
- PostgreSQL 자체 로그: stderr로 출력하고 Docker 로그로 수집
- 영속성: PostgreSQL 데이터는 Docker named volume에 저장
- 로그 보존기간: 7일
- 시간 형식과 타임존: ISO 8601 UTC
- CloudWatch Logs: 3일 MVP 범위에서 제외
- 시크릿·개인정보: 기록 금지
- 도구 호출: 허용된 호출의 종류·결과·소요시간만 기록하고 민감한 인자는 제외

## 16. 검증 및 완료 기준

### 16.1 정상 흐름 검증

- 예시 입력이 다섯 개의 올바른 합산 행으로 변환된다.
- 총 인원 수가 `6명`으로 표시된다.
- `민수`, `서연`, `지훈`, `수빈`, `현우`, `지민`이 최종 결과에 각각 정확히 한 번 포함된다.
- 사이즈가 없는 모든 주문에 톨이 적용된다.
- `휘핑 제외`와 `샷 추가`가 옵션이 다른 별도 행으로 유지된다.

### 16.2 장애 흐름 검증

| 장애 | 완료 증거 |
|---|---|
| 에이전트 타임아웃 | 10초 초과 감지, 시도·대기 이력, 정상 결과 또는 안전 중단 |
| 에이전트 처리 실패 | 실패 분류, 제한적 재시도 또는 모의 대체 모델, 검증 결과 |
| PostgreSQL·메뉴 조회 실패 | 재연결 시도, 복구 시 정상 조회 또는 실패 시 회로 차단·상태 보존 |
| 동일 장애 반복 | 3회 상한, 60초 냉각, 추가 실행 차단, 수동 확인 요청 기록 |

### 16.3 완료 판정

- 모든 필수 기능 요구사항이 검증 가능한 증거를 가진다.
- 성능·오류율·자동 복구율·커버리지 기준을 측정할 수 있다.
- 복구 실행과 복구 검증이 분리돼 있다.
- 장애별 MTTD·MTTR 및 최종 상태를 산출할 수 있다.
- 범위 밖 기능이 결과물에 포함되지 않는다.

> 이 섹션은 검증 기준만 정의한다. 오늘 코드·테스트·장애 주입을 생성하거나 실행하지 않는다.
