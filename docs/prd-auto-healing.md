## 2. 프로젝트 개요

Group Coffee Order Agent는 최대 20명의 참여자로부터 구조화된 채팅 방식으로 커피 주문을 수집하고, 고정된 모의 메뉴를 기준으로 메뉴·사이즈·옵션을 정규화하며, 누락·중복·오류를 검증해 총무가 매장 직원에게 보여줄 수 있는 최종 주문서를 생성하는 교육용 서비스다.

프로젝트는 주문 처리 중 모의 메뉴 조회 또는 주문 저장 의존 서비스에 장애가 발생했을 때 이를 탐지·진단하고, 허용된 정책 안에서 복구한 뒤 독립적으로 정상화를 검증하는 Auto Healing 흐름을 제공한다.

기술 제약조건은 Python, FastAPI, Docker 및 Docker Compose이며, 실제 브랜드 시스템이나 결제 시스템에는 연결하지 않는다.

## 3. 문제 정의

현재 단체 커피 주문은 10명 이상의 참여자가 공유 스프레드시트에 이름과 메뉴를 직접 입력하고, 총무가 이를 들고 매장에서 다시 주문하는 방식이다. 이 과정에서 메뉴명과 옵션 표현이 제각각이고, 주문 누락·중복·오입력이 발생할 수 있으며, 총무가 모든 주문을 수동으로 대조해야 한다.

디지털 주문 수집 시스템을 사용하더라도 메뉴 조회 또는 주문 저장 의존 서비스가 실패하면 주문 확정이 지연되거나 누락될 수 있다. 운영자는 로그와 주문 현황을 확인하고 실패 요청을 수동으로 재시도해야 하며, 잘못된 재처리는 중복 주문을 만들 수 있다.

서비스 경계는 참여자의 주문 입력부터 총무를 위한 최종 주문서 생성까지다. 실제 매장 주문, 결제, 환불 및 브랜드 시스템 연동은 경계 밖이다.

## 4. 사용자와 이해관계자

| 구분 | 역할과 요구 |
|---|---|
| 주문 참여자 | 자신의 메뉴·사이즈·옵션을 입력하고 모호한 항목을 확인·수정한다. |
| 주문 총무 | 참여 현황을 확인하고 주문을 마감하며 최종 주문서를 확인한다. |
| 매장 직원 | 총무가 제시한 읽기 쉬운 합산 주문서를 확인한다. 시스템 사용자는 아니다. |
| 운영자 역할의 팀원 | 자동 복구 실패와 승인 요청을 검토하고 후속 조치를 결정한다. |
| 교육생·검토자 | 장애 재현성, 복구 안전성, 측정 결과와 요구사항 충족 여부를 검토한다. |

## 5. 목표와 성공 기준

1. 최대 20명의 주문을 수집하고 총무가 수동으로 주문 접수를 마감할 수 있어야 한다.
2. 확정 주문에는 참여자 식별자, 유효한 메뉴, 사이즈와 필수 옵션이 있어야 하며 참여자별 확정 주문은 하나만 존재해야 한다.
3. 최종 주문서를 참여자별 내역과 메뉴별 합산 내역을 포함한 Markdown 표 및 JSON 형식으로 생성해야 한다.
4. 메뉴 조회 HTTP 5xx, 메뉴 조회 3초 초과, 주문 저장 연결 실패를 서로 구분해 탐지하고 사건을 생성해야 한다.
5. 각 장애에 대해 최대 3회, 1·2·4초 지수 백오프로 복구를 시도하고 성공 여부를 판정해야 한다.
6. 동일 장애가 3회 연속 실패하면 30초 동안 회로를 차단하고, 추가 자동 시도를 중단한 뒤 사람에게 에스컬레이션해야 한다.
7. 30초 후 헬스체크와 독립 기능 검증이 모두 성공한 경우에만 요청 처리를 재개해야 한다.
8. 각 사건에서 MTTD, MTTR, 복구 시도 횟수, 진단 근거와 최종 상태를 기록해야 한다.

## 7. 정상 서비스 시나리오

1. 총무가 최대 참여자 수 20명인 단체 주문 세션을 연다.
2. 참여자가 구조화된 채팅 입력으로 이름 또는 가상 식별자와 주문 내용을 제출한다.
3. 수집 역할이 주문 입력을 접수한다.
4. 메뉴 정규화 역할이 모의 메뉴 조회 서비스를 사용해 메뉴·사이즈·옵션을 표준화한다.
5. 내용이 모호하거나 필수 옵션이 없으면 참여자에게 되묻고 확정 전까지 저장하지 않는다.
6. 확정된 주문을 모의 주문 저장 서비스에 저장한다.
7. 검증 역할이 누락·중복·유효하지 않은 메뉴와 필수 옵션을 확인한다.
8. 총무가 주문을 수동으로 마감한다.
9. 정산 역할이 참여자별 내역과 메뉴별 합산 내역을 Markdown 표 및 JSON으로 출력한다.

## 9. 멀티 에이전트 구성

주문 업무 역할 4개는 서비스의 사용자 가치 흐름을 담당한다. 장애 대응 역할은 책임 분리를 위한 개념적 역할이며, 3일 MVP 구현에서는 책임·권한·독립 검증을 유지하는 범위에서 통합할 수 있다.

### 수집 에이전트

- 책임: 구조화된 채팅 주문 접수와 참여자 식별
- 입력: 참여자 식별자와 주문 내용
- 출력: 접수된 원시 주문
- 사용할 수 있는 정보: 현재 주문 세션과 참여자 입력
- 허용 행동: 입력 형식 확인, 주문 접수
- 금지 행동: 메뉴 임의 확정, 실제 주문 전송
- 실패 시 행동: 오류를 반환하고 주문을 미확정 상태로 유지

### 메뉴 정규화 에이전트

- 책임: 메뉴·사이즈·옵션 표준화 및 모호한 입력 재질문
- 입력: 원시 주문과 모의 메뉴 데이터
- 출력: 정규화 주문 또는 확인 질문
- 사용할 수 있는 정보: 고정된 모의 메뉴와 옵션 규칙
- 허용 행동: 메뉴 매칭, 필수 항목 확인, 재질문
- 금지 행동: 메뉴 데이터에 없는 항목을 임의 생성
- 실패 시 행동: 주문을 확정하지 않고 장애 대응 흐름에 신호 전달

### 주문 검증 에이전트

- 책임: 누락·중복·유효하지 않은 메뉴 및 옵션 확인
- 입력: 정규화 주문과 저장 결과
- 출력: 검증 결과와 수정 필요 항목
- 사용할 수 있는 정보: 세션 참여 현황, 모의 메뉴, 확정 주문
- 허용 행동: 조회, 비교, 오류 표시
- 금지 행동: 검증 없이 주문을 정상으로 선언하거나 데이터를 임의 수정
- 실패 시 행동: 주문서 생성을 중단하고 총무에게 알림

### 정산 에이전트

- 책임: 최종 주문서 집계와 출력
- 입력: 마감된 검증 완료 주문
- 출력: Markdown 표와 JSON 주문서
- 사용할 수 있는 정보: 검증 완료된 주문 데이터
- 허용 행동: 참여자별·메뉴별 집계
- 금지 행동: 결제 수행, 검증되지 않은 주문 포함
- 실패 시 행동: 주문서 생성을 실패 상태로 유지하고 총무에게 알림

### Monitor Agent

- 책임: 장애 신호 관찰과 사건 생성
- 입력: 헬스체크, HTTP 상태, 응답시간, 연결 오류, 로그
- 출력: 사건 식별자와 증거를 포함한 장애 사건
- 사용할 수 있는 정보: 모의 서비스 상태와 요청 지표
- 허용 행동: 상태 조회와 사건 생성
- 금지 행동: 복구 실행과 설정 변경
- 실패 시 행동: 관찰 실패 자체를 운영자에게 알림

### Diagnosis Agent

- 책임: 증거에 따라 장애 유형 분류와 복구전략 권고
- 입력: 장애 사건과 관련 증거
- 출력: 장애 분류, 근거, 권고 복구전략
- 사용할 수 있는 정보: 사건 로그, 응답 상태, 시간과 연결 오류
- 허용 행동: 증거 조회와 규칙 기반 분류
- 금지 행동: 복구 직접 실행과 근거 없는 원인 확정
- 실패 시 행동: 자동 변경 없이 사람에게 에스컬레이션

### Recovery Agent

- 책임: 승인된 정책 안에서 제한된 복구 실행
- 입력: 분류된 장애와 승인된 복구전략
- 출력: 시도 횟수, 결과와 실행 증거
- 사용할 수 있는 정보: 해당 사건, 이전 시도와 허용목록
- 허용 행동: 제한된 재시도, 연결 회복 후 중복 방지 재처리
- 금지 행동: 임의 명령, 실제 데이터 변경, 허용목록 밖의 재시작
- 실패 시 행동: 시도 상한에서 중단하고 Orchestrator에 반환

### Verification Agent

- 책임: Recovery Agent와 독립적으로 정상화와 주문 무결성 검증
- 입력: 사건, 복구 결과, 정상 기준
- 출력: 정상화 또는 실패 판정과 증거
- 사용할 수 있는 정보: 헬스체크, 독립 기능 요청, 확정 주문 상태
- 허용 행동: 읽기 전용 상태·기능·무결성 검증
- 금지 행동: 복구 실행, Recovery Agent 보고만으로 성공 선언
- 실패 시 행동: 사건을 종료하지 않고 실패 판정 반환

### Orchestrator

- 책임: 사건 상태, 역할 호출 순서, 재시도, 회로 차단과 에스컬레이션 관리
- 입력: 장애 사건과 각 역할의 결과
- 출력: 다음 실행 상태, 종료 또는 에스컬레이션 결정
- 사용할 수 있는 정보: 전체 사건 이력과 정책
- 허용 행동: 역할 호출, 정책 적용, 상태 전환
- 금지 행동: 정책 우회, 직접 데이터 수정과 임의 복구
- 실패 시 행동: 자동 흐름을 안전하게 중단하고 사람에게 알림

### Notification Agent

- 책임: 총무 또는 운영자에게 승인 요청과 사건 결과 전달
- 입력: 사건 상태, 근거, 필요한 사람 행동
- 출력: 알림 또는 승인 요청
- 사용할 수 있는 정보: 보고에 필요한 최소 사건 정보
- 허용 행동: 상태와 증거 전달
- 금지 행동: 복구정책 변경과 승인 대행
- 실패 시 행동: 사건 로그에 전달 실패 기록

## 10. 에이전트 협업 흐름

### 정상 주문 흐름

참여자 입력 → 수집 → 메뉴 정규화 → 주문 저장 → 주문 검증 → 총무 마감 → 정산 → 최종 주문서

### 장애 대응 흐름

장애 신호 → Monitor 사건 생성 → Diagnosis 분류 → Orchestrator 정책 확인 → Recovery 제한 복구 → Verification 독립 검증

- 검증 성공: 정상화 시각과 증거를 기록하고 사건 종료
- 검증 실패 및 시도 여유 있음: 다음 백오프 후 재시도
- 3회 실패: 회로 차단, 자동 복구 중단, Notification을 통한 에스컬레이션
- 30초 경과: 헬스체크와 독립 기능 검증을 수행하고 모두 성공할 때만 회로 재개

| 메뉴 조회 HTTP 5xx | 5xx와 오류 로그 | HTTP 상태와 대상 서비스 | 1·2·4초 간격 재시도 | 회로 차단 후 에스컬레이션 | 3 | 상한 초과 후 추가 시도 | 추가 변경 없음, 요청 미확정 유지 | 정상 조회 및 주문 정규화 성공 |

## 12. 자율성과 Human-in-the-loop

### 자동 실행 가능

- 실패한 모의 메뉴 조회를 정책 범위에서 재시도
- 연결 회복 후 사건의 동일 주문을 중복 없이 재처리
- 헬스체크와 읽기 전용 독립 검증
- 3회 연속 실패 시 회로 차단
- 30초 냉각 후 재개 조건 검사

### 사람 승인 후 실행

- 복구 상한을 넘는 추가 시도
- 허용목록 밖의 서비스 변경 또는 재시작
- 확정 주문을 변경해야 하는 조치
- 원인 불명 장애에 대한 후속 조치

### 자동 실행 금지

- LLM이 임의로 생성한 명령 실행
- 실제 주문·결제·환불
- 운영 데이터 수정·삭제
- 인증정보 변경
- 비용 제한 없는 인프라 생성·확장
- 허용목록 밖의 서비스 재시작

## 13. 기능 요구사항

### FR-001 주문 세션과 주문 수집

- 설명: 총무는 최대 20명의 주문을 받을 세션을 운영하고 수동으로 마감할 수 있다.
- 입력: 참여자 식별자와 구조화된 주문 내용
- 기대 동작: 마감 전 주문을 접수하고 마감 후 신규 주문을 거부한다.
- 예외 상황: 인원 초과, 중복 참여자, 마감 후 요청
- 인수조건: 20명까지 접수되고 21번째 요청과 마감 후 요청은 명확한 사유와 함께 거부된다.

### FR-002 메뉴 정규화와 재질문

- 설명: 주문을 고정된 모의 메뉴·사이즈·옵션과 대조한다.
- 입력: 원시 주문과 모의 메뉴 데이터
- 기대 동작: 유효한 주문은 표준 형태로 변환하고 모호하거나 필수 항목이 없으면 되묻는다.
- 예외 상황: 메뉴 조회 5xx 또는 3초 초과, 존재하지 않는 메뉴
- 인수조건: 메뉴 데이터에 없는 항목을 임의 확정하지 않으며, 미확정 주문은 최종 주문서에 포함되지 않는다.

### FR-003 주문 저장과 중복 방지

- 설명: 확정 주문을 모의 저장소에 저장한다.
- 입력: 참여자 식별자와 정규화 주문
- 기대 동작: 동일 주문의 재처리에서도 참여자별 확정 주문이 하나만 유지된다.
- 예외 상황: 저장소 연결 실패 또는 불완전 저장
- 인수조건: 연결 복구 후 재처리해도 중복이 없고 저장 성공 여부가 기록된다.

### FR-004 주문 검증

- 설명: 주문서 생성 전에 누락·중복·유효하지 않은 메뉴와 옵션을 검사한다.
- 입력: 참여 현황, 모의 메뉴와 확정 주문
- 기대 동작: 오류 목록 또는 검증 통과 결과를 반환한다.
- 예외 상황: 미확정 주문 또는 검증에 필요한 데이터 조회 실패
- 인수조건: 검증 실패 상태에서는 총무가 주문을 마감해도 최종 주문서를 정상 완료로 표시하지 않는다.

### FR-005 최종 주문서 생성

- 설명: 검증 완료된 주문을 참여자별 및 메뉴별로 집계한다.
- 입력: 마감된 검증 완료 주문
- 기대 동작: Markdown 표와 JSON 주문서를 생성한다.
- 예외 상황: 검증되지 않은 주문 존재 또는 집계 불일치
- 인수조건: 두 출력의 총 주문 수와 메뉴별 수량이 일치한다.

### FR-006 장애 사건 생성

- 설명: 지정 장애를 관찰하면 고유 사건을 생성한다.
- 입력: HTTP 상태, 응답시간, 연결 오류와 로그
- 기대 동작: 사건 식별자, 추적 식별자, 탐지 시각, 장애 유형 후보와 증거를 기록한다.
- 예외 상황: 장애 유형을 분류할 증거 부족
- 인수조건: 세 가지 지정 장애마다 사건이 생성되고 증거 부족 시 원인 불명으로 에스컬레이션된다.

### FR-007 제한된 자동 복구

- 설명: 분류된 장애에 승인된 복구전략만 적용한다.
- 입력: 장애 유형, 시도 횟수와 정책
- 기대 동작: 최대 3회, 1·2·4초 지수 백오프로 재시도한다.
- 예외 상황: 원인 불명, 정책 상한 초과, 허용목록 밖의 조치 필요
- 인수조건: 3회 이후 추가 자동 시도가 없고 금지 행동이 실행되지 않는다.

### FR-008 회로 차단과 재개

- 설명: 반복 실패로 인한 무한 복구를 방지한다.
- 입력: 동일 장애의 연속 실패 횟수
- 기대 동작: 3회 실패 시 30초 동안 회로를 차단하고 자동 복구를 중단한다.
- 예외 상황: 냉각시간 후 헬스체크 또는 독립 검증 실패
- 인수조건: 두 검증이 모두 성공한 경우에만 회로가 닫히며, 실패하면 차단 상태와 에스컬레이션이 유지된다.

### FR-009 독립 복구 검증

- 설명: 복구 실행 주체와 분리된 검증이 정상화를 판정한다.
- 입력: 사건, 복구 결과와 정상 기준
- 기대 동작: 헬스체크, 핵심 기능과 주문 무결성을 확인한다.
- 예외 상황: 검증 요청 실패 또는 기준 미충족
- 인수조건: Recovery Agent의 성공 보고만으로 사건이 종료되지 않는다.

### FR-010 알림과 에스컬레이션

- 설명: 자동 복구 실패와 사람의 결정이 필요한 사건을 보고한다.
- 입력: 사건 요약, 증거, 시도 이력과 권고 행동
- 기대 동작: 운영자 역할의 팀원에게 필요한 정보를 전달한다.
- 예외 상황: 알림 전달 실패
- 인수조건: 전달 성공 또는 실패가 사건 이력에 기록된다.

## 14. 비기능 요구사항

### NFR-001 안전성

자동 행동은 모의 환경과 허용목록으로 제한되며 실제 주문·결제·운영 데이터 및 임의 명령을 사용하지 않아야 한다.

### NFR-002 신뢰성과 멱등성

동일 주문 저장을 재처리해도 참여자별 확정 주문이 중복 생성되지 않아야 한다.

### NFR-003 관측 가능성

모든 사건은 탐지부터 종료 또는 에스컬레이션까지 동일한 사건·추적 식별자로 연결되어야 한다.

### NFR-004 성능

정상 상태의 모의 메뉴 조회는 3초 이내에 결과를 반환해야 한다.

### NFR-005 재현성

세 가지 지정 장애는 실제 데이터 손상 없이 격리된 Docker Compose 환경에서 반복 재현할 수 있어야 한다.

### NFR-006 설명 가능성

장애 분류, 복구전략 선택, 성공·실패 판정에는 사용된 증거와 규칙이 기록되어야 한다.

### NFR-007 데이터 최소화

가상 참여자 식별자와 모의 주문 데이터만 사용하고 인증정보·결제정보·실제 개인정보를 기록하지 않아야 한다.

## 15. 데이터와 로그 요구사항

### 주문 데이터

- 주문 세션 식별자
- 가상 참여자 식별자
- 원시 입력과 정규화된 메뉴·사이즈·옵션
- 주문 확정·검증·마감 상태
- 중복 방지를 위한 주문 식별자

### 사건 로그

- incident_id와 trace_id
- injected_at, detected_at, recovery_started_at, recovered_at
- 대상 서비스, 장애 유형, 탐지·진단 근거
- 선택한 복구전략, 시도 횟수, 백오프 시간과 결과
- 회로 상태와 재개 검사 결과
- 사람 승인 또는 에스컬레이션 결과
- 독립 검증 결과와 최종 상태

### 시간과 지표

- MTTD = detected_at - injected_at
- MTTR = recovered_at - injected_at
- 복구 실행시간 = recovered_at - recovery_started_at
- 시간은 ISO 8601 형식과 Asia/Seoul 기준으로 기록한다.

### 민감정보와 보존

- 실제 개인정보·결제정보·인증정보는 수집하거나 기록하지 않는다.
- 로그 저장 위치와 보존 기간은 `[미결정]`이며, 3일 실습 범위를 넘는 운영 보존정책은 정의하지 않는다.
